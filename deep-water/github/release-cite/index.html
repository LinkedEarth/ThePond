Release and Cite your Work

Learn how to create a release, add citation information, and connect your repository to Zenodo.

Overview

You’ve created a research repository, tracked changes, collaborated through pull requests, and used Issues to organize your work. But how do you share a version of your research that someone else can reliably find, reuse, and cite?

A GitHub repository is a living project: files change, analyses evolve, and new features or corrections are added. A release identifies a particular version of that work, making it easier for others to understand exactly what was available at a given point in time.

In this Deep End Pad, you’ll prepare your repository for its first release. You’ll consider reuse permissions, create citation information, choose a version number, write release notes, and explore how GitHub releases can be preserved in a research archive such as Zenodo.

You’ll also discover why a GitHub release, an archived version with a DOI, a published dataset, and a research paper are not interchangeable—even when they are all part of the same research project.

The goal isn’t simply to make files available. It’s to help other researchers understand what you’ve shared, what they can do with it, and how to give your work appropriate credit.

What you will learn

By the end of this Pad, you will be able to:

  • Evaluate release readiness: Check whether your repository is sufficiently documented and identify scientific, technical, or permission-related issues that need attention.
  • Understand licensing: Recognize why a public repository isn’t automatically available for reuse and identify licensing questions for code, data, and documentation.
  • Create citation metadata: Add a CITATION.cff file so GitHub can display instructions for citing your work.
  • Choose a version: Understand common versioning approaches, including semantic versioning (v1.0.0) and calendar-based versioning (v2026.10.26).
  • Prepare a GitHub release: Identify a version of your project, write meaningful release notes, and prepare a release using GitHub’s interface.
  • Understand archival and DOIs: Explain how Zenodo can preserve a release, what a DOI identifies, and why individual versions may have different DOIs.
  • Make your work easier to cite: Add clear citation and version information to your README and understand how that information evolves with subsequent releases.

A note about publishing

This Pad distinguishes between preparing a release and publishing one.

If you’re using the water-quality training project, you’ll complete the GitHub activities, including creating CITATION.cff and preparing a draft release. You’ll explore DOI creation through a simulated example rather than depositing the training repository in Zenodo.

Why? Zenodo is intended to preserve research outputs for long-term discovery and citation. Creating many permanent records of the same training exercise would add little scientific value.

If you’re working on your own research project and have the necessary permissions, you can follow the optional publishing pathway to release and archive your work.

Preparing a release does not mean your research is automatically ready to publish. Identifying missing information, unresolved scientific concerns, or permissions that need clarification is an important part of the process.

What exactly are you releasing?

Imagine that another research group wants to use your work. They found your GitHub repository, but they have a few questions:

  • Which version of the analysis should they use?
  • Where can they find the data?
  • Can they retrieve exactly the same files you used?
  • What should they cite?

These questions may have different answers.

A research project can produce several related outputs, each serving a different purpose.

One project, several research products

Consider our water-quality project, where we’re studying nitrate concentrations at monitoring stations.

Research product What does it provide?
GitHub repository The evolving project, including notebooks, documentation, history, and ongoing work.
GitHub release An identified version of the project, linked to a Git tag, with release notes and downloadable files.
Archived version A preserved copy of a particular version, which may be deposited in a research repository such as Zenodo and assigned a DOI.
Dataset The underlying observations or measurements, which may have their own repository, version, and citation.
Research paper The scientific questions, methods, results, and interpretations, with its own citation.

These products are connected, but one does not automatically replace the others.

For example, citing a paper about nitrate concentrations does not necessarily identify the exact notebook version used to produce its figures. Likewise, citing the notebook does not replace crediting the original data providers.

How do GitHub releases fit in?

A GitHub release is built around a tag, which identifies a particular point in the repository’s history.

Think of it this way:

  • Your main branch continues to evolve as you make changes.
  • A tag identifies a particular state of the files.
  • A GitHub release uses that tag and adds useful information, such as a version name and release notes.
  • A research archive such as Zenodo can preserve a version and provide a DOI for citation.

A GitHub release does not automatically create a DOI. And although GitHub provides downloadable ZIP files for releases, downloading a ZIP is not the same as depositing a version in a research archive.

TipWhen should you create a release?

That depends on what you’re developing.

For a scientific workflow, a release often accompanies a research milestone, such as a paper submission or publication. This helps preserve the exact analysis used to produce the reported results.

For research software, releases usually follow meaningful changes to the software, such as new functionality, improvements, or bug fixes. They don’t need to wait for a publication.

In both cases, the goal is to identify a version that others can reliably use. We’ll explore how to decide when a release is warranted later in this Pad.

NoteWhat about “Archive this repository” on GitHub?

GitHub also has an Archive this repository feature. It makes the repository read-only, generally indicating that development is no longer active.

This is different from preserving a particular release in Zenodo. You can continue developing your GitHub repository while archiving individual versions elsewhere.

The key idea is that a repository represents an evolving project, while a release identifies a particular state of that project.

Neither automatically guarantees scientific quality, long-term preservation, or appropriate citation. Those require additional decisions, which we’ll explore throughout this Pad.

Is your repository ready for release?

Before creating a release, it’s worth examining what another researcher would actually receive.

Imagine downloading a research workflow. The notebook opens, but you cannot find the input data. Or perhaps the data are included, but nobody documented their source, units, or quality-control procedures.

The files may be available, but availability alone doesn’t make a research product reusable or scientifically reliable.

Preparing a release is an opportunity to identify these problems.

This doesn’t mean every Issue must be closed or that the project must be finished. Research and software continue to evolve. What matters is that the version you release has a clear purpose, is sufficiently documented, and does not misrepresent what it can do.

What should you check?

Before releasing a research workflow or software project, consider six areas.

Area Questions to ask
Documentation Can someone understand what the project does, what the files contain, and where to start?
Data and provenance Are input data identified? Can others find them and understand their sources, units, and processing?
Reproducibility Are instructions, dependencies, and required software versions documented sufficiently for someone to use the work?
Scientific or technical correctness Are there known errors that could affect results or users? Are important limitations documented?
Sharing permissions Are there restricted data, credentials, third-party materials, or other constraints on what can be shared?
Authorship and responsibility Do you know who contributed and who has authority to approve publication?

We’ll address two additional requirements later in this Pad: selecting a license and creating citation metadata. You don’t need to have those completed yet.

ImportantA known error doesn’t disappear when you make a release

Remember the water-quality project from our earlier Pads?

We identified a scientific problem: the notebook averages nitrate replicates before excluding measurements with failed quality checks. We discussed correcting the methodology, but the notebook itself has not yet been fixed.

Publishing this workflow as a validated analysis could mislead other researchers.

That doesn’t prevent us from preparing the repository for a future release. It means the correction remains an open task, and we should not publish the current notebook as a validated scientific product.

The same principle applies to software: not every open Issue prevents a release, but a bug that compromises important results or functionality may need to be resolved before publishing.

A release-readiness review is most useful when it leads to action.

You may have identified missing instructions, data-access questions, scientific errors, or decisions that require input from other team members.

On GitHub:

  1. If you found an important problem, check whether it already has an Issue.

CautionWhat if you discover information that should not have been shared?

If you discover a password, API key, restricted dataset, or other sensitive information in your repository, do not publish a release.

Next, we’ll examine an important distinction: just because someone can see your work doesn’t mean they have permission to reuse it. That’s where licensing comes in.

Can others reuse your work?

You’ve checked whether your repository is ready for release. Now imagine another researcher discovers it and wants to adapt your notebook for a different study.

They can see the files on GitHub. But does that mean they’re allowed to modify and redistribute them?

Not necessarily. A public GitHub repository is not automatically open source.

Without an explicit license or other permission, copyright law generally restricts what others can do with the work, beyond the permissions granted through GitHub’s terms of service.

A license explains what others are permitted to do with material you’ve shared, such as using, modifying, and redistributing it, and under what conditions.

One repository, different kinds of material

Research repositories often contain more than one type of material.

Material What should you consider?
Code and notebooks Software licenses such as MIT, BSD, Apache, or GPL may be appropriate for code you are authorized to license.
Data Data may come with their own license, access conditions, or restrictions. Original datasets may use licenses or public-domain tools such as CC BY or CC0.
Documentation and figures These may use licenses such as Creative Commons, or be covered by the project’s software license when appropriate.
Third-party material You cannot simply assign a new license to material you don’t have the rights to license.

For repositories containing several kinds of material, you may need different licenses or additional notices explaining which permissions apply to which files.

ImportantLicensing and citation are not the same thing
  • Licensing addresses what someone is permitted to do with your work.
  • Citation tells someone how to credit the research product they used.

A license may include attribution requirements, but providing a citation does not automatically grant permission to reuse material. Likewise, permission to reuse something does not eliminate the need for appropriate scholarly credit.

We’ll create citation metadata in the next part.

Return to your GitHub repository.

Step 1: Find out what is already licensed

  1. On the Code tab, look for a file named LICENSE, LICENSE.md, or a similar name.
  2. If one exists, open it. What does it permit, and which files does it cover?
  3. Check your README for licensing information about code, data, documentation, or other materials.
  4. Consider whether you have permission to distribute and license everything included in the repository.

For the water-quality project, think about the notebooks, synthetic measurements, figures, and documentation. Even when data are synthetic, you should establish who can authorize their redistribution.

Step 2: Decide what you can do

You have two possible paths.

Path A: You have permission to choose a license

If you own or have authority to license the relevant material and have already selected an appropriate license:

  1. On GitHub, select Add file → Create new file.
  2. Name the file LICENSE.
  3. Select Choose a license template.
  4. Review the available licenses and select the one you’ve decided to use.
  5. Follow GitHub’s instructions to review and submit the license.
  6. Commit the change, using a message such as Add project license.

If your repository includes materials covered by different licenses, clarify their scope in your README. Don’t imply that the new license covers material for which you cannot grant rights.

Return to the repository’s main page. For a recognized standard license, GitHub may display the license information in the repository’s About area.

Path B: You need more information or authorization

Perhaps your repository contains data from another institution, was developed with collaborators, or includes material whose licensing terms are unclear.

In that case, don’t choose a license just to finish the exercise.

Instead, create a GitHub Issue titled:

Confirm licensing and reuse permissions before release

In its description, identify:

  • Which materials need licensing clarification.
  • Whose permission or advice you need.
  • What needs to be decided before publication.

You can also add a short licensing-status statement to your README, making clear that permissions are still being reviewed.

This is a useful outcome: you’ve identified an obstacle to reuse and made it visible to the project team.

Next, we’ll tackle the other side of sharing research: how should someone cite your work?

Tell others how to cite your work

Imagine that another researcher has successfully used your nitrate analysis workflow. They now want to acknowledge your work in a publication.

But what should they write in their reference list?

They could link to your GitHub repository, but a URL alone doesn’t tell them who created the workflow, what its title is, or which version they used.

Scientific workflows should be cited as research products in their own right, independently of the papers that describe or use them. This applies to your own workflows, too!

In fact, many scientific publishers now require formal citations for the data and computational tools supporting published research. For example, the American Geophysical Union (AGU) guidelines require authors to cite the data and software or code used in their studies—including code they developed themselves—in the paper’s reference list. Authors must also explain where these research products can be accessed in a Data and Software Availability Statement.

So, if you’re publishing a paper based on your own analysis notebooks, you should cite the workflow itself, not just the paper describing the results. Ideally, that citation will identify the exact version used to produce the published findings.

That’s where CITATION.cff comes in.

A CITATION.cff file contains structured information about how your research product should be cited. It uses a format called Citation File Format (CFF), which is readable by both people and software.

When you add this file to the root of your GitHub repository, GitHub can display a Cite this repository link and generate citations in APA and BibTeX formats.

This makes it easier for others—and for you when preparing your own publications—to cite your workflow correctly. Later in this Pad, we’ll see how to connect this citation information to a specific release and its DOI.

What’s in a citation file?

A CITATION.cff file can contain:

Field Purpose
title The name of the software, workflow, or research product
authors The people or organizations who should receive citation credit
message A short explanation of how you would like the work cited
repository-code Where the source repository is located
version The version of the research product
date-released When that version was released
doi A persistent identifier for the research product, if available
orcid A persistent identifier for an individual author, if available

You don’t need every field immediately. In particular, you shouldn’t invent a release date, version, or DOI for work that hasn’t been released yet.

Who should be listed as an author?

Authorship deserves some thought.

GitHub records who contributes commits, but GitHub contributors and citation authors aren’t necessarily identical. For example, someone who helped design the scientific methodology may deserve authorship even if they never committed a file.

The author list should reflect the project’s agreed attribution practices. Author order may matter, especially in scientific research.

You can include ORCID identifiers to help distinguish researchers with similar names. These should be the actual identifiers of the authors.

TipORCID

An ORCID iD is a persistent identifier for a researcher. It helps connect publications, datasets, software, and other research contributions to the correct person, even when names change or multiple researchers have similar names.

ORCID identifiers are optional in CITATION.cff, but including them when available makes research credit more reliable.

Activity: Create your citation file

Let’s create a citation file for your repository.

Step 1: Start with a template

If you’re using the water-quality training project, you can start with the example below. The project title and group author are illustrative; they are not claims of actual authorship.

If you’re using your own repository, replace them with the correct title and agreed authorship information.

cff-version: 1.2.0
message: "If you use this workflow, please cite it using these metadata."
title: "Water-Quality Nitrate Analysis Workflow (training example)"
authors:
  - name: "Water-Quality Training Project (example)"
repository-code: "https://github.com/OWNER/REPOSITORY"

Replace OWNER/REPOSITORY with the information from your GitHub repository URL.

For your own research, you will usually want to list individual authors. For example, the authors section could instead look like this:

authors:
  - family-names: "FIRST_AUTHOR_FAMILY_NAME"
    given-names: "FIRST_AUTHOR_GIVEN_NAME"
  - family-names: "SECOND_AUTHOR_FAMILY_NAME"
    given-names: "SECOND_AUTHOR_GIVEN_NAME"

Replace the placeholders with the actual names, in the agreed order.

If an author has an ORCID iD, add an orcid field under their name, using the complete https://orcid.org/... URL.

NoteA few details about YAML

CITATION.cff uses YAML, a plain-text format for structured information.

  • Spaces and indentation matter. Use spaces, not tabs.
  • Each field has a name followed by a colon (:).
  • The - before an author marks an entry in a list.
  • Quotation marks help keep titles and other text containing special characters intact.

You don’t need to learn YAML in depth for this exercise. Follow the template carefully and edit the information it contains.

Step 2: Add the file to GitHub

  1. Open your repository on GitHub and select the Code tab.
  2. Select Add file → Create new file.
  3. Name the file exactly CITATION.cff. It should be in the repository’s top-level directory, alongside your README.
  4. GitHub may suggest a citation-file template. You can replace that content with the template above, adapted to your project.
  5. Review the content, particularly the title, authors, and repository URL.
  6. Click Commit changes… and use a message such as Add citation metadata for research workflow.
  7. Commit the file. If you’re working on a branch, merge the change into the repository’s default branch using a pull request, as you practiced in Pad 3.

You have now added structured citation information to your research repository.

Step 3: See what GitHub does with it

Return to the repository’s main page on its default branch.

Look for Cite this repository in the right sidebar.

  1. Select Cite this repository.
  2. Look at the citation GitHub generates in APA format.
  3. Examine the BibTeX citation.
  4. Check whether the title and authors match what you intended.
  5. If something is incorrect, edit CITATION.cff, commit the correction, and check again.
TipDon’t see “Cite this repository”?

First check that:

  • The filename is exactly CITATION.cff.
  • The file is in the repository’s root directory.
  • The change is present on the default branch (usually main).
  • The YAML structure and indentation are correct.

If GitHub still cannot interpret the file, you can use the Citation File Format initializer to construct a citation file with guided validation, or consult the CFF schema documentation.

Seeing GitHub’s citation display is a useful functional check, but it isn’t a substitute for full schema validation.

Two different kinds of version numbers

You probably noticed that our example starts with:

cff-version: 1.2.0

Does that mean your workflow is already at version 1.2.0?

No! There are two different version fields.

cff-version: 1.2.0
version: "1.0.0"
  • cff-version identifies the version of the Citation File Format specification. For the format used here, it remains 1.2.0 even when you update citation information.
  • version identifies the version of your workflow, software, or dataset. This changes when you create a new version of your research product.

You should keep the research-product version consistent with the release being described. When you create a new release, review the version, date-released, and doi fields together.

You do not need to change either version number every time you correct a typo in CITATION.cff.

For now, we haven’t added a research-product version to the training example because we haven’t created a release. We’ll revisit this in the next sections.

What if your workflow also has a paper?

Many scientific workflows accompany a research paper, and software projects may also have a methods or software publication.

The paper and the workflow are related, but they are different research products.

For example:

  • The paper describes the research question, scientific results, and interpretation.
  • The workflow citation identifies the computational work used to generate or analyze the results.
  • The data citation acknowledges the measurements or other source data used in the analysis.

Depending on how someone uses the work, they may need to cite more than one of these. The paper communicates the scientific findings, while the workflow citation credits the computational methods and implementation used to produce them. Researchers should cite the workflow independently of the paper, along with the underlying datasets when appropriate.

CITATION.cff also supports a field called preferred-citation, which can instruct GitHub to recommend an associated paper instead of the repository itself.

That can be useful in some projects, but it changes what GitHub generates when someone chooses Cite this repository.

For this exercise, we’ll keep the citation focused on the workflow or software itself. Later, we’ll add clear instructions to the README explaining how to cite the repository and any associated research products.

NoteYour citation will evolve with the project

When your project receives its first versioned release, you’ll update CITATION.cff with the appropriate version and release date.

If you archive that release in Zenodo and obtain a DOI, you can update the citation information again.

Remember that GitHub displays citation information from the default branch. That information may describe the latest release, while someone reproducing an earlier study needs to cite the specific version they used.

An archived, version-specific citation helps with that distinction.

What have you accomplished?

Your repository now tells other researchers how to give credit to the people or team responsible for the work.

You have also seen that citation metadata is separate from licensing, GitHub’s commit history, and any associated publications.

If you’re using the training repository, keep its citation clearly identified as an exercise. Do not add a fictional DOI or claim that the workflow has been scientifically validated.

Next, we’ll decide when a project deserves a new version, how to name that version, and what belongs in useful release notes.

Choose a version and write release notes

Your repository has changed since you first created it. You’ve added documentation, tracked Issues, collaborated on changes, and prepared citation information.

But not every commit needs a new release.

A release identifies a meaningful version of your project that others can refer to, retrieve, and potentially use.

Two decisions are involved:

  1. When should you create a release?
  2. How will you identify that version and describe what has changed?

When should you create a release?

The answer depends partly on what you’re developing.

Research workflows Research software
Releases often accompany research milestones, such as conference presentation, paper submission or publication. Releases often follow meaningful development milestones, such as new features, bug fixes, or important improvements.
The goal may be to preserve the exact analysis used to produce published results. The goal may be to provide users with an identifiable, tested version of the software.
A correction that changes scientific results may warrant a new release. An important bug fix may warrant an immediate release, even if no new features have been added.

These aren’t rigid rules. You may release a workflow before publication to support peer review, or release software alongside a paper.

The important question is whether the version represents a meaningful, identifiable state of the research product.

TipWhat about unresolved Issues?

You don’t need to close every Issue before creating a release. Some Issues represent future improvements, feature requests, or long-term research goals.

However, an unresolved issue that compromises the scientific results or essential functionality may prevent a release from being suitable for its intended purpose.

Remember our water-quality project: the notebook still averages replicates before excluding measurements with failed QC. We identified the problem, but we haven’t corrected the notebook.

That correction might eventually justify a new version. For now, we must not describe it as completed or publish the current workflow as a validated analysis.

How do you number versions?

There isn’t one versioning system that works best for every research project. Two common approaches are semantic versioning and calendar versioning.

Semantic versioning: v1.2.3

Semantic versioning, often called SemVer, uses three numbers:

1
Major
Breaking changes
.
2
Minor
New functionality
.
3
Patch
Compatible bug fixes

In software, the convention is:

  • Major (1 → 2): Changes that break compatibility with the previous public interface, such as removing or substantially changing an API.
  • Minor (2 → 3): New functionality that remains compatible with the previous interface.
  • Patch (3 → 4): Bug fixes that preserve compatibility.

For example, if software at v1.2.3 receives a compatible bug fix, its next version might be v1.2.4.

If a new compatible feature is introduced, it might become v1.3.0.

And if an API changes in a way that requires users to modify their existing code, it might become v2.0.0.

NoteWhat about workflows?

Workflows don’t always have a public API in the same sense as software.

You can adopt a similar numbering convention, but you should explain what major, minor, and patch changes mean for your workflow.

For example, a major change might alter the expected input structure or fundamentally change how the workflow is used.

A correction to a scientific method might appear small in the code but substantially change the results. Don’t assume that every scientific correction is automatically a minor patch.

The Semantic Versioning specification provides the formal rules for software that uses SemVer.

Version numbers beginning with 0, such as 0.1.0, are commonly used during early development. Under SemVer, 1.0.0 marks a defined public interface, not proof that the software or scientific results are error-free.

The v is a common prefix for Git tags; the three numbers are the semantic version itself.

Calendar versioning: v2026.10.26

Another approach is calendar versioning, or CalVer.

Instead of describing compatibility through version numbers, the version includes a date.

For example:

v2026.10.26

Component Meaning
2026 Year
10 Month
26 Day

This approach can be particularly useful for scientific workflows, where releases correspond to research milestones or dated snapshots.

A workflow might have a release associated with a paper submission, followed by another release several months later incorporating additional analyses.

The date identifies when the release was made, but it doesn’t explain what changed or guarantee compatibility. That’s why release notes remain important.

Calendar versioning has several possible formats. For this Pad, we’ll use vYYYY.MM.DD. If you make multiple releases on one day, you’ll need a consistent way to keep their tags unique.

You can learn more at CalVer.org.

TipWhich should you use?

If you’re developing software with a defined API, semantic versioning often communicates compatibility more effectively.

If you’re developing a scientific workflow tied to research milestones, calendar versioning may be easier to interpret.

Neither system is mandatory. Choose a convention that makes sense for your project and use it consistently.

Don’t change an existing project’s versioning convention without a good reason.

From commits to a release

You’ve already learned that Git records changes through commits and that branches, such as main, allow development to continue.

A release introduces another Git concept: the tag.

A tag identifies a particular commit in your repository’s history. While main can advance as new commits are added, a version tag is intended to continue pointing to the commit selected for that version.

A GitHub release is built around that tag.

GitHub feature What does it represent?
Commit A recorded change or set of changes
Branch (main) A line of development that advances as changes are added
Tag (v1.0.0) A name identifying a specific commit
Release A published version associated with a tag, including release notes and downloadable files
Draft release A release being prepared but not yet published

Once a release is published, GitHub automatically offers downloadable source-code archives (ZIP and tar.gz) corresponding to its tag.

NoteA draft release isn’t a published snapshot

When you create a draft release using a new tag name, GitHub can save the draft without creating the actual Git tag until you publish.

This means the draft describes a proposed version, but the final snapshot may not yet be fixed.

If main changes before publication, the new tag could identify a different state of the project than you originally intended.

For a real publication, verify the intended commit and tag before publishing. An existing tag pointing to the reviewed commit provides a more reliable starting point.

Archive your release and obtain a DOI

You’ve prepared a GitHub release. Once it’s published, other researchers can retrieve the files associated with that version.

But how do you make the research product easier to discover, preserve, and cite over the long term?

One solution is to deposit it in a research repository such as Zenodo.

Zenodo is a general-purpose research repository that supports many kinds of research outputs, including software, workflows, datasets, and documentation. It assigns Digital Object Identifiers (DOIs) to deposited research products.

A DOI provides a persistent identifier that can be used in publications, reference lists, and research documentation.

GitHub and Zenodo work well together:

  • GitHub supports the ongoing development of your research project.
  • Zenodo preserves identifiable versions of that work and provides persistent identifiers for citation.

You don’t need to choose between them. In fact, Zenodo can connect to GitHub and automatically archive new releases.

ImportantUsing the water-quality training project?

Do not publish your draft release or connect the training repository to Zenodo for this exercise.

Zenodo creates persistent scholarly records. We don’t want to fill the archive with multiple copies of the same educational exercise, particularly one containing an unresolved scientific problem.

You’ll explore DOI creation through an interactive simulation instead.

If you’re working on your own research repository, are authorized to publish it, and have completed the necessary release-readiness checks, you can follow the optional publishing pathway below.

Two DOIs for one research project?

When Zenodo archives the first version of a research product, it normally registers two different DOIs.

They serve different purposes.

DOI What does it identify? When should you use it?
Version DOI One specific archived version, such as v1.0.0 When citing the version used for a scientific analysis or software application
Concept DOI (all versions) The research product as a whole, across its different versions When referring to the overall project rather than a particular release

Every subsequent archived version receives a new Version DOI, but the Concept DOI stays the same.

The Concept DOI currently directs readers to the latest archived version, while individual Version DOIs continue to identify their corresponding versions.

This distinction is crucial for reproducibility.

Imagine that your paper used version v1.0.0 of a nitrate analysis workflow. A year later, the team releases v2.0.0, which implements a different method.

Someone attempting to reproduce your published results needs the original version, not the latest one.

That’s why scientific publications should normally cite the Version DOI corresponding to the workflow or software actually used.

Read more in Zenodo’s DOI versioning documentation.

Zenodo Version DOI A new DOI is assigned to each newly archived version.
Zenodo Concept DOI Stays the same across all versions. The project-level README badge can remain unchanged.
Older releases Remain identifiable and citable. Don’t silently replace them with newer versions.

The order matters

For a repository connected to Zenodo, the typical sequence is:

  1. Before the release: Complete and validate the changes. Update the project version and citation metadata. Make sure the new release’s metadata does not incorrectly point to the previous version’s DOI.
  2. Publish the release: Create the new tag and GitHub release once the project is ready. If Zenodo integration is enabled, it can automatically archive the release.
  3. After archival: Obtain the new Version DOI from Zenodo and update CITATION.cff and the README’s citation instructions.
  4. Check the result: Confirm that GitHub’s Cite this repository displays the intended citation and that the README links are correct.

Remember that CITATION.cff on the default branch normally describes the version you currently recommend citing. Earlier publications should continue citing the specific versions they used.

NoteDon’t confuse a new commit with a new release

You don’t need to change the research-product version in CITATION.cff after every commit.

During development, you may make dozens of commits before creating another release.

When preparing a new version, however, check that the version metadata matches the research product being released.

And remember: cff-version: 1.2.0 describes the citation-file format. It isn’t your software or workflow version.

Activity: Your release maintenance plan

Step 1: Review what you’ve prepared

Check the following items against your actual repository.

If you’ve published and archived your own research product, also verify that your DOI badge, citation metadata, and Zenodo record point to the intended research product and versions.

You don’t need a real DOI to complete this checklist.

Step 2: Identify what would justify the next release

Open your repository’s Issues tab.

Find an unresolved scientific or technical Issue and consider:

  • Would resolving this Issue warrant a new release, or could it wait for a larger research milestone?
  • What would need to be tested or validated before that release?
  • Would the change affect existing users or previously published scientific results?

For the water-quality example, revisit the outstanding QC correction.

Once that correction has actually been implemented and validated, a new version could document the methodological change and any impact on the results.

You can record release-related tasks in the existing Issue if useful. Don’t close the Issue until the underlying work is genuinely resolved.
