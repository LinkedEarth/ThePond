Start a Research Repository

Learn what Git and GitHub each do, then create and describe a well-organized research repository.

A research repository gives the files associated with a project a shared home. It can help you keep track of your work, explain it to others, and prepare it for collaboration or publication.

In this Pad, you will create a GitHub repository for a supplied geoscience project. If you prefer, you can use one of your own research projects instead.

What you will learn

By the end of this Pad, you will be able to:

  • explain the difference between Git and GitHub;
  • decide what belongs in a research repository—and what does not;
  • create a repository on GitHub; and
  • write a README that helps someone understand the project;

What you will need

  • A GitHub account
  • A web browser. We recommend using the latest version of Chrome, Firefox, or Safari for the best experience.
  • Approximately 15-20 minutes
  • Optional: Your own files to share on GitHub. If you do not have any research project that you are willing to share publicly on GitHub yet, you can use the supplied geoscience project for this activity.

You do not need prior experience with Git or GitHub. You will complete this activity through GitHub’s website; no command-line tools are required.

Git and GitHub are not the same thing

Although their names are similar, Git and GitHub play different roles.

Git is a version-control system. It records changes to files over time, allowing you to examine the history of a project or return to an earlier version. Git can work locally on your computer without an internet connection.

GitHub is an online platform that hosts Git repositories. It also provides tools for sharing projects, discussing work, reviewing proposed changes, and organizing tasks.

A Git repository can exist without GitHub, and GitHub is not the only service that can host Git repositories.

Plan your research repository

A research repository should contain the files needed to understand, inspect, and—when possible—reproduce the work. That does not mean every file associated with a project belongs in GitHub.

Decide where project files belong

GitHub works well for versioning code, notebooks, documentation, configuration instructions, and reasonably sized files that you have permission to share.

Other files need a different approach.

Type of file What to do Why
Code, notebooks, documentation, and small shareable data Include in GitHub These files help others understand and reproduce the work.
API keys, passwords, access tokens, and other login credentials Do not include in GitHub Anyone who obtains the credential may be able to access the associated account or service.
Large data files Store elsewhere and document Large data generally belong in an appropriate data repository. The README can link to the data and identify the version used.
Restricted or sensitive data Store in an approved access-controlled location and document The README can describe the data and explain how authorized researchers may request access.
Data created by someone else Check permission before deciding Downloading data does not necessarily grant permission to redistribute them. Check the license and terms of use.
Temporary files and copies created only to preserve an earlier version Do not include in GitHub Git already records the history of tracked files.
Generated figures and results Include when they are meaningful research products Important outputs can help readers understand the study even when they can also be regenerated.

Credentials and .env files

Projects sometimes need an API key, access token, username, or another local setting.

A common approach is to:

  1. Create a local .env file.
  2. Add .env to .gitignore before entering any credentials.
  3. Enter the credentials only after Git has been told to ignore the file.
  4. Document the required variable names in the README without including their values.

The .env filename is only a convention. Git does not automatically protect it.

WarningIgnoring a file does not erase its history

If a file has already been committed, adding it to .gitignore does not remove it from earlier commits.

If a credential is accidentally committed, treat it as exposed and replace or revoke it.

NoteComing in the next Pad: .gitignore

A .gitignore file tells Git which untracked files it should leave out of commits. It is commonly used for local .env files, caches, temporary files, and software-generated files.

You will create and use a .gitignore file in Save and Share Changes, when you begin working with the repository on your computer.

TipUsing your own project

You may use your own research project instead. Begin with files that you have permission to share and that do not contain credentials, restricted information, or sensitive data.

If you are uncertain, create a private repository. However, some of the later exercises in the GitHub deep dive may require a public repository.

After downloading the study package:

  1. Unzip the package.
  2. Look through its folders and files.
  3. Keep the files together so that you can upload the complete project structure.

2. Create the repository

Open GitHub’s new repository page.

Complete the form using the following guidance:

  • Owner: Select your personal account or the organization where the project belongs. For funded projects, you should discuss with the principal investigator where they want the repository.
  • Repository name: Use a short, descriptive name such as stream-water-quality. Names must be unique for that account (personal or organization).
  • Description: Write one sentence describing the scientific question.
  • Visibility: A supplied study may be public or private. For your own research, choose private if you are uncertain about sharing any materials yet. Repositories should be made publicly available once the results are published.
  • Add a README file: Select this option.
  • Add .gitignore: Leave this set to None for now.
  • Choose a license: Leave this set to None for now.

Then select Create repository.

NoteWhat about the license?

A public repository is not automatically open for reuse. Choosing a license requires considering what the repository contains and whether you have permission to share it.

Licensing will be covered in a separate Deep End Pad. For now, leave Choose a license set to None.

3. Add the study files

On the repository page:

  1. Select Add file.

  2. Select Upload files.

  3. Open the unzipped study package on your computer.

  4. Drag all of the supplied project files and folders into the upload area.

  5. Check that the files and folder structure appear in the list.

  6. In the commit message field, enter:

    Add study files

  7. Select Commit changes.

You have now added the working materials to the repository. GitHub recorded this upload as a change in the repository’s history.

4. Write the README

Return to the repository’s main page and open README.md.

Select the pencil icon to edit it. Replace the initial contents with information that helps a new visitor understand the project.

You can use this structure:

# Project title

## Research question

State the scientific question addressed by this study.

## Project summary

Briefly explain what the study examines and why.

## Repository contents

Describe the purpose of the main files and folders.

- `analysis.ipynb`:
- `data/`:
- `figures/`:
- `environment.yml`:

## Data

Describe each dataset used by the study. Delete any sections below that do not apply.

### Data included in this repository

For data stored in the repository, describe:

- what the data represent;
- who created or published them;
- the relevant dates, locations, variables, and units;
- the file format;
- any processing already applied; 
- the license or terms governing their use; and
- citation for the dataset, if applicable

### Data stored elsewhere

For large data or data deposited in another repository, provide:

- the name of the repository or archive;
- a link or DOI;
- the dataset version or access date;
- the files used in this analysis; 
- instructions for obtaining the data;
- citation for the dataset, if applicable.

### Restricted or sensitive data

If data cannot be shared publicly, explain:

- what data are not included;
- why access is restricted;
- where the data are stored; 
- how an authorized researcher can request access; and
- citation for the dataset, if applicable.

Do not include restricted values or sensitive details in the README itself.

### Data created by someone else

For third-party data, provide:

- the original creator or publisher;
- a citation and link to the original source;
- the version or date accessed;
- the license or terms of use; and
- instructions for obtaining the data when redistribution is not permitted.

### Synthetic data

If the study uses synthetic data, explain:

- that the values are simulated rather than observations;
- why the synthetic data were created;
- how they were generated;
- whether a random seed was used; and
- where the generation code can be found.

## How to reproduce the analysis

Explain the main steps needed to run the notebook.

## Contributors

List the people responsible for the project.

## Acknowledgments

Recognize any individuals, organizations, or funding sources that contributed to the project.

Adapt the filenames and sections to match the study package you selected.

NoteFormal citation information comes later

A CITATION.cff file provides structured citation information for a repository. GitHub can use it to display a recommended citation.

You will create this file in Release and Cite Your Work, together with a versioned release and DOI.

When the README is ready:

  1. Select Commit changes.

  2. Use a short commit message such as:

    Document the study

  3. Confirm the commit.

Return to the repository’s main page. GitHub should display the rendered README beneath the file list.
