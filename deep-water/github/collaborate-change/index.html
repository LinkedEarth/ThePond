Collaborate on GitHub

Learn to collaborate on research projects using GitHub branches, pull requests, and scientific reviews. Practice proposing, discussing, and merging changes.

Overview

Research is rarely a solitary activity. A colleague may notice that a dataset needs better documentation, question an analysis decision, or suggest a clearer way to present results. But how do we make these improvements without disrupting someone else’s work? And how do we preserve the discussions and decisions that led to a change?

GitHub provides a way to propose, discuss, and review changes before incorporating them into a shared project. In this LilyPad, you’ll use branches and pull requests to improve your own repository while participating in a simulated collaboration on a scientific research project. You’ll discover that contributing to research involves more than writing code: reviewing documentation, questioning scientific assumptions, and providing constructive feedback are equally valuable.

What you will learn

By the end of this LilyPad, you will be able to:

  • Work on a branch: Create and manage a branch in GitHub Desktop to propose changes without directly modifying main.
  • Propose an improvement: Make a focused change, commit and publish it, and open a pull request on GitHub.
  • Review scientific changes: Examine changes to documentation and Jupyter notebooks, recognizing which changes may affect scientific interpretation or reproducibility.
  • Participate in a review: Use comments, approvals, and requests for changes to provide constructive feedback.
  • Respond to feedback: Revise your work and update an existing pull request.
  • Merge and synchronize: Incorporate an accepted change into main and update your local repository.

Before you begin

For this LilyPad, you’ll need:

  • A GitHub account and GitHub Desktop installed on your computer.
  • The research repository you created in Starting a Research Repository on GitHub and cloned to your computer in Save and Share Changes on GitHub.
  • A small improvement you could make to your project, such as clarifying documentation, adding information about your data, or correcting an explanation.

You don’t need to know Python or find a collaborator to complete this LilyPad.

You’ll work in two environments:

  • Your own repository on GitHub: You’ll create a branch, make a change, open a pull request, and eventually merge it.
  • An interactive research scenario in The Pond: You’ll take part in a fictional collaboration, reviewing proposed changes and responding to scientific questions through activities that simulate GitHub’s interface.

Meet your research collaborators

Throughout this LilyPad, we’ll follow a fictional research team investigating whether nitrate concentrations change as a stream flows through a developed area.

The researchers are working together on a GitHub repository containing their data documentation and an analysis notebook. As they improve their study, they need to propose changes, examine each other’s work, and decide when those changes are ready to become part of the project.

You’ll take on the role of a collaborator, helping the team evaluate proposed changes. You’ll examine documentation, inspect notebook changes, and participate in simulated pull-request discussions. No programming expertise is required: your scientific reasoning is what matters.

At the same time, you’ll practice the corresponding GitHub actions in your own repository.

Let’s begin by exploring why researchers might want to work on separate branches.

Part 1 - Why work on a branch?

Imagine you’re part of a research team investigating how nitrate concentrations change as a stream flows through a developed area.

Your colleague is working on the analysis notebook, while you’ve noticed that the README.md could better explain how the measurements were collected and checked for quality. You both need to make changes to the same research repository. But what happens if you make changes directly to the version everyone else is using?

Of course, collaborators aren’t always working on different files. Sometimes, two researchers need to modify the same notebook, dataset description, or analysis script. When their changes overlap, Git may not be able to combine them automatically. This is called a merge conflict, and we’ll return to it later.

Keeping shared work stable

When you create a GitHub repository, it typically starts with a branch named main. Think of this as the primary version of your research project.

A branch allows you to work on a proposed change without immediately incorporating it into main. You can experiment, revise your work, and ask others to review it before deciding whether the change should become part of the shared project.

For example, your team might have:

  • main — the primary version of the study.
  • improve-data-documentation — a branch for clarifying the data descriptions.
  • update-analysis-methods — another branch for improving the analysis notebook.

All three branches belong to the same repository. Changes made and committed to one branch don’t automatically become part of the others.

Branches make it easier to work on different improvements independently. Later, a pull request will allow you to propose incorporating your branch’s changes into main.

Part 2 - From improvement to proposal

You’ve created a branch where you can work independently without immediately changing main. Now it’s time to use it!

A small change can make a big difference

Let’s return to our water-quality research team.

Your colleague is updating the analysis notebook, while you’re improving the project’s documentation. You’ve noticed that the README.md doesn’t clearly describe where the nitrate measurements came from or how their quality was assessed.

You could simply edit the README and add your changes directly to main. But what if your colleague has questions about the documentation? Or notices that something important is missing?

This is where a pull request becomes useful.

A pull request (often abbreviated PR) allows you to propose changes from one branch into another. Instead of incorporating changes immediately, you create a space where collaborators can:

  • See exactly what changed.
  • Understand why the change was proposed.
  • Ask questions and suggest improvements.
  • Review the changes before they’re incorporated into main.

Importantly, a pull request is not limited to code. You can propose changes to documentation, analysis notebooks, figures, or any other files tracked in your repository.

How does a pull request work?

A branch allows you to work on a proposed change without immediately modifying main. But how do you eventually incorporate that change into the shared project?

That’s where a pull request comes in.

A pull request (often shortened to PR) allows you to propose changes from one branch to another, usually into main. It gives collaborators an opportunity to examine, discuss, and improve those changes before they’re incorporated into the project.

Think of it as saying to your collaborators:

“I’ve made some improvements to the project. Here’s what I changed and why. Could you take a look before we incorporate them?”

When you open a pull request, GitHub compares two branches:

  • Base branch: Where you want your changes to go (usually main).
  • Compare branch: The branch containing your proposed changes.

GitHub then shows the differences between them, allowing collaborators to examine what was added, removed, or modified.

A pull request provides a space where researchers can:

  1. Propose: Describe what changed and why.
  2. Discuss: Ask questions, identify problems, and suggest improvements.
  3. Revise: Make additional changes in response to feedback.
  4. Merge: Incorporate the accepted changes into the target branch.

Importantly, opening a pull request does not change main. Your proposed changes remain on your branch until they are merged.

Why is this useful for research?

Imagine that our water-quality team wants to update how nitrate measurements are handled.

One researcher proposes changing the analysis, but another notices that the new method might exclude scientifically meaningful observations.

A pull request allows them to discuss that decision before incorporating the change into the shared analysis. The discussion also provides a record of why the team made its decision.

This is one of GitHub’s benefits for research: it helps preserve not only what changed, but also the reasoning behind the change.

Your turn: Make a meaningful improvement

Now let’s work with your own research repository.

1. Choose an improvement

Think of one small change that would make your project easier for someone else to understand or use.

For example, you could:

  • Clarify where your data came from.
  • Add information about the units of measurement or the meaning of a variable.
  • Explain an analysis parameter or a scientific decision.
  • Improve instructions for reproducing an analysis.
  • Clarify a description in a notebook’s Markdown cell.

Choose something that is genuinely useful for your project. You don’t need to modify Python code.

2. Make the change

  1. Open GitHub Desktop and select your research repository.
  2. Check that Current Branch shows the branch you created in Part 1, not main.
  3. Open the relevant file in your preferred text editor.
  4. Make your improvement and save the file.
Tip

If you’re using one of the supplied study packages, you can work with its README.md or the Markdown cells in its notebook. You don’t need to invent scientific information. Focus on clarifying information already available in the project.

3. Review and commit your change

Return to GitHub Desktop.

  1. Select the Changes tab.
  2. Click the file you modified to inspect the differences.
  3. Look at the highlighted lines. Red indicates removed content, while green indicates added content.
  4. Make sure the changes reflect what you intended and don’t include unrelated modifications.
  5. Enter a descriptive message in the Summary field, such as Clarify data sources in README.
  6. Click Commit to [your branch name].

Remember from Save and Share Changes on GitHub: a commit records a meaningful checkpoint in your project’s history.

Publish your branch

So far, your branch and its new commit exist on your computer.

To make the branch available on GitHub:

  1. In GitHub Desktop, click Publish branch in the top toolbar.
  2. Wait for the publication to finish.
  3. Open your repository on GitHub and locate your new branch.

Your changes are now available on GitHub, but they have not been incorporated into main.

This is an important distinction: publishing a branch makes your work available; opening a pull request proposes incorporating it into another branch.

Open your first pull request

Let’s turn your improvement into a proposal.

  1. Return to GitHub Desktop and click Preview Pull Request.
  2. Confirm that the base branch is main and your new branch contains the proposed changes.
  3. Click Create Pull Request. GitHub Desktop will open GitHub in your browser.
  4. Give your pull request a descriptive title.
  5. Write a short description that explains:
    • What changed? What did you add, remove, or clarify?
    • Why? How does the change improve the research project?
    • What should be checked? Is there something you’d want a collaborator to examine?
  6. Click Create pull request on GitHub.

For example, our fictional water-quality team might write:

Title: Clarify nitrate data documentation

What changed: Expanded the README to describe the data source and the quality-control information.

Why: The previous documentation did not provide enough information for another researcher to understand how the dataset was assembled.

What to check: Are the descriptions sufficiently clear for someone unfamiliar with the study?

Notice that the description focuses on the research improvement, not just which file was modified.

Take a look at your pull request

Your pull request should now be marked Open on GitHub.

Explore the interface briefly:

  • Conversation contains the pull request description and any subsequent discussion.
  • Commits shows the commits included in the proposed change.
  • Files changed allows collaborators to inspect the differences between the branches.

Don’t merge your pull request yet! We’ll return to it after exploring the review process.

ImportantKeep your pull request open

We’ll use this same pull request later in the LilyPad to practice responding to feedback, making another commit, and merging the accepted change.

Part 3 - Reviewing a scientific change

You’ve opened a pull request in your own repository. Before a proposed change becomes part of a shared research project, someone should consider not just whether the files changed as intended, but whether the scientific workflow still makes sense.

Now you’ll act as a reviewer for our fictional stream-water-quality team. You won’t need a collaborator or any Python knowledge to complete the review.

How a pull-request review works

In a GitHub pull request, Files changed shows the differences between the proposed branch and the target branch. A reviewer can select a changed line using the + icon, write a comment, and start a review. Comments in a pending review aren’t submitted until the reviewer finishes it.

GitHub provides three ways to submit a review:

  • Comment: Share feedback without explicitly approving the change or requesting revisions.
  • Approve: Indicate that the proposed changes are ready to merge.
  • Request changes: Ask the author to revise the proposal before merging. Whether this formally blocks merging depends on the repository’s settings.

A scientific review should consider whether the changes are justified, clear, and reproducible. Reviewers can contribute valuable insights by examining the methods and documentation, even if they don’t write code.

Try it: Review the team’s pull request

Our team measures nitrate concentrations at different stations along a stream. Some station–date pairs have replicate measurements. Each individual measurement has a quality-control flag:

  • qc_complete = 1: the measurement has been checked and accepted for analysis.
  • qc_complete = 0: the quality check is incomplete, so the measurement is not yet accepted for analysis. This does not necessarily mean the measurement is erroneous.

A teammate proposes changing the order in which the analysis handles quality control and averages replicates. Your task is to assess the proposal as a collaborator, rather than simply verifying that the code runs.

  1. Read the proposed change in Conversation.
  2. Open Files changed. Examine README.md and analysis.ipynb. You can switch to a readable notebook preview if the JSON diff is difficult to follow.
  3. Think about what happens when some, or none, of the replicates for a station and date are accepted. Is the proposed method—and the documentation—clear enough?
  4. Click a blue + beside a changed line, write a review comment in your own words, and select Start a review.
  5. Click Review changes, choose Comment, Approve, or Request changes, then click Submit review.

After submitting, you’ll see one possible scientific review to compare with your own. The simulation stays on this page; nothing is posted to GitHub.

Why did the notebook diff look strange?

A Jupyter notebook (.ipynb) is stored as JSON. It contains Markdown text, code, metadata, execution counts, and sometimes saved outputs. A source diff can therefore look quite different from the notebook you read in Jupyter—even when a change is scientifically straightforward.

GitHub can display notebooks as readable static pages when browsing a repository, but source diffs may expose JSON details or be harder to review. In this simulation, Notebook preview is a teaching aid that lets you examine the scientific narrative and sample observations without deciphering Python or JSON. In a real review, you can ask the author to explain a change, inspect a rendered notebook when available, or open it in Jupyter.

The important distinction is between incidental file changes (such as a changed execution count) and changes that affect which observations enter an analysis. Saved notebook outputs can be scientifically meaningful too; they shouldn’t automatically be dismissed.

But a reviewer raised a question: what happens when no measurements at a station and date have passed quality control? A good pull request gives collaborators a place to resolve that question before the change reaches main.

Your turn: Update your open pull request

Now return to the real pull request you created in Part 2. You don’t need a real reviewer: use the perspective you practiced in Part 3 and identify one additional improvement to your own changes. For example, you might clarify a data source, explain a quality-control decision, or make a documentation instruction easier to follow. Avoid inventing research details you don’t know.

  1. In GitHub Desktop, select your repository and make sure Current Branch is the branch used for your open pull request, not main.
  2. Edit the relevant file locally, then save it.
  3. Return to GitHub Desktop and inspect the new changes in the Changes tab.
  4. Write a focused commit message, such as Clarify treatment of excluded observations, and click Commit to [your branch name].
  5. Select Push origin to send that commit to GitHub. (If Desktop offers Publish branch instead, check that you’re on the branch you published in Part 2.)
  6. Open your existing pull request in GitHub. Check Commits and Files changed. Your new commit should appear in that same pull request—no second PR is necessary.
TipWhy not open another pull request?

A pull request follows changes on a particular branch. When you push another commit to that branch, GitHub incorporates it into the open PR. That lets reviewers follow the evolution of a single proposal and the decisions made along the way.

Merge your improvement

A collaborator would normally assess the updated proposal and provide approval when appropriate. Because you’re working independently, your own inspection is not an independent review, and you cannot approve your own pull request on GitHub. For this exercise, you can merge your own PR if the repository’s settings permit it.

  1. Open your pull request on the GitHub website and confirm its Files changed tab shows the intended final edits.
  2. Return to Conversation and find Merge pull request. If your repository allows the merge, select it and then Confirm merge. If the button is unavailable, read GitHub’s explanation rather than changing project rules simply to finish the activity.
  3. Once the pull request is merged, GitHub may offer Delete branch. You may delete the remote working branch, since the accepted changes are now in main.

Notice that merging updates main on GitHub. Your local copy of main still needs to catch up.

Synchronize your local repository

  1. Return to GitHub Desktop.
  2. Open Current Branch and switch to main. Before switching, make sure you don’t have uncommitted local edits that could interfere.
  3. Click Fetch origin to check for changes on GitHub. If Desktop shows Pull origin, click it to bring the merged commits into your local main.
  4. Verify that your edited file now contains the merged improvement, even though you’re on main rather than your working branch.
  5. Optionally delete the local working branch when you’re sure you no longer need it. Deleting a branch is different from deleting the commits already merged into main.
ImportantKeep the roles distinct
  • Commit saves your change locally on the current branch.
  • Push origin sends new local commits to GitHub and updates an open PR based on that branch.
  • Merge pull request incorporates the accepted change into the remote main branch.
  • Fetch origin / Pull origin helps update your local main after the merge.

Check your progress

By the end of this activity, you should have a merged pull request in your GitHub repository, at least two commits documenting the improvement and its revision, and a local main branch that contains the final changes.

As you look back at your pull request, notice what the process preserved: not just what changed, but why it changed and how a proposed improvement became part of the research project.

[Optional] Going further: collaborating beyond your own repository

You’ve now proposed, reviewed, revised, and merged a change. That workflow works well when you have permission to create branches in the shared repository and Git can combine everyone’s work automatically.

But research collaborations don’t always work that way. Here are two situations you may encounter. Both activities are optional; you do not need to complete them to finish this LilyPad.

What if you cannot publish a branch to the project?

Imagine that Priya, a researcher outside our water-quality team, notices that the repository could explain its quality-control flags more clearly. She wants to propose an improvement, but she isn’t a member of the team and doesn’t have permission to push branches to stream-team/stream-water-quality.

She can still contribute to a public repository using a fork.

A branch is a separate line of work within a repository. A fork is a separate repository under another account, connected to the original project (often called the upstream repository).

Priya can edit and push to a branch in her fork, then open a pull request proposing that the original project incorporate those changes. The maintainers of the original repository decide whether to review and merge the contribution. The review process is much like the one you just practiced; the main difference is where the proposed branch lives.

NoteWhy not always use a fork?

If you already have write access to the research team’s repository, working in a branch there is generally simpler. Forks are especially useful when contributing to projects you don’t maintain, such as open-source research software or public documentation.

Optional hands-on: Explore a fork

If you know of a public research repository you genuinely want to contribute to, try the following. There’s no need to submit an unsolicited pull request just to practice.

  1. Open the repository on GitHub and look for its contribution instructions. Notice how the maintainers prefer people to propose changes.
  2. Click Fork, choose Create a new fork if prompted, select your account as the owner, and click Create fork.
  3. Look at the heading of your fork. GitHub identifies the original repository from which it was forked.
  4. If you want to explore locally, clone your fork in GitHub Desktop and create a branch there. Changes you publish belong to your fork, not to the upstream project.
  5. Before opening a real pull request, make sure your change is useful and follows the project’s contribution instructions. In a pull request from a fork, the base repository is the original project and the head/compare branch comes from your fork.

If you don’t have an appropriate repository in mind, it’s fine to simply examine the GitHub guide to forking. You can return to this workflow when a real opportunity arises.

What if two branches change the same lines?

Earlier, we mentioned that branches let researchers work independently, but they do not prevent every problem when work is combined.

Imagine a different outcome for our water-quality team’s pull request: before Maya’s change is merged, Alex updates the same sentence of README.md on main to clarify the measurement units. Maya has rewritten that sentence on her branch to explain which measurements are included in an average.

Both changes are reasonable. But they affect the same part of the file, and Git cannot confidently decide which wording to keep. This is a merge conflict.

Git may show a conflict using markers such as these:

<<<<<<< main
Measurements are summarized by station and date; nitrate concentrations are in mg/L.

If this happens in a real pull request

When GitHub detects a conflict, it may prevent merging the pull request until the conflicting content is resolved. For simple text conflicts, you may be able to click Resolve conflicts on GitHub, edit the file, remove the conflict markers, then select Mark as resolved and Commit merge. More complicated cases may require resolving the conflict locally. GitHub’s conflict-resolution guide walks through the process.

The important lesson: A merge conflict is not necessarily a mistake. It means Git needs a person to decide how to combine competing changes. In scientific work, that decision may depend on the meaning of the data or methods, not just the text.

Before you leave the pond

You’ve now taken a research improvement from a branch to a pull request, practiced reviewing a scientific decision, updated a proposal, and merged it into the project. You have also seen how the same ideas extend to outside contributors and overlapping edits.

Consider your next collaborative project: What is one change you would want another researcher to review before it becomes part of the shared work? It might be a data-processing choice, a unit conversion, a methods description, or a figure caption. The value of a pull request is not limited to code—it is also the chance to catch errors, discuss decisions, and preserve the reasoning behind research changes.
